What I Learned Debugging a Memory Leak for Three Days Straight

Faheem · Aug 22, 2026 · 14.6 KB read

It wasn't the allocator, the GC, or the framework. It was a closure holding a reference nobody meant to keep — and it took three days, four false leads, and one very ugly heap snapshot to find it.

The symptom was simple: memory climbed steadily on a page that should have had a flat footprint. No crashes, no errors in the console — just a tab that got heavier the longer it stayed open, until the browser eventually gave up.

Day one: chasing the wrong thing

My first instinct was the usual suspect — event listeners piling up on every re-render. I stripped them out one component at a time, watched the memory graph, and got nothing. The line kept climbing at the same steady rate, completely indifferent to what I'd just removed.

If removing code doesn't change the graph, you're not looking at the code that matters.

That line, scribbled in my notes at the end of day one, is the only thing that kept me from giving up on day two.

Day two: the heap snapshot that actually mattered

Chrome's DevTools memory panel lets you take two snapshots and diff them. I'd tried this before and skimmed past the results — too much noise, too many retained objects with names like (closure) and (array). This time I let it sit for ten minutes between snapshots instead of ten seconds, and the noise fell away. One retainer had grown by over four thousand instances.

// heap_snapshot.diff + retained: onScroll closure × 4,812 + size: 2.1 MB and climbing - listener never unbound on unmount

A scroll listener, attached in a component that mounted and unmounted constantly as the user navigated a list. The listener was never removed. Every mount created a new closure over the component's state, and every one of those closures stayed alive in memory long after the component was gone — kept there by the one thing I hadn't thought to check: the browser's own event target.

Day three: the fix, and the lesson

The fix was one line — a cleanup function returned from the effect that attached the listener in the first place. Unglamorous, obvious in hindsight, and easy to miss because nothing about it threw an error.

// fix: 1 line, 3 days later return () => el.removeEventListener('scroll', onScroll)

The real lesson wasn't about scroll listeners. It was that a leak rarely announces itself where you're looking. The code that's growing isn't always the code that's guilty — it's usually whatever's holding a reference to it. Once I started asking "what's keeping this alive" instead of "what's creating too much," the search got a lot shorter.

Next time, I'm reaching for the heap diff on day one, not day two.
